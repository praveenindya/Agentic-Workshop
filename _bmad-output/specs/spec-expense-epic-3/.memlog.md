- (note) Input: PRD Success Metrics (SM-1/2/3, counter-metric SM-C1), cases/expense/BRIEF.md 'How it's checked' section, cases/expense/eval/labelled.csv (30 claims, columns line_id/claim_id/expected_decision/expected_clause -- no amount column), spec-expense-epic-2's SPEC.md (upstream agent contract), and triage's spec-epic-3 as the pattern to mirror. Slug expense-epic-3 per the disambiguation convention -- spec-epic-3 already exists in this tree as triage's.
- (capability) CAP-1: a person can run an entrypoint to evaluate the Epic 2 agent over every claim in eval/labelled.csv in one pass, logging exactly one MLflow run.
- (capability) CAP-2: decision_match scorer -- 1 when a line item's decision equals expected_decision, 0 otherwise, for all labelled line items.
- (capability) CAP-3: clause_match scorer -- 1 when a line item's cited clause equals expected_clause, 0 otherwise.
- (capability) CAP-4: reimbursable_total_match scorer -- per claim, 1 when the sum of amounts (from seed/line_items.csv, joined by line_id) of agent-approved items equals the same sum computed from expected_decision labels, 0 otherwise.
- (capability) CAP-5: a Groq-hosted judge scores each line item's explanation clarity and clause-citation correctness (SM-3), calling ChatGroq via JUDGE_MODEL/GROQ_API_KEY, never GEMINI_API_KEY.
- (capability) CAP-6: the run reports its flag-rate (share of decisions that are 'flag') alongside the primary scores, so a trivial always-flag strategy (SM-C1's counter-metric) is visible, not hidden behind a high match rate.
- (capability) CAP-7: after the run, a person can see and reuse the eval's scores without opening the MLflow UI -- printed means plus a written report file.
- (capability) CAP-8: the same judge-scoring pipeline can run against a single claim id that has no label -- enabling live scoring of the 10 holdout claims one at a time during the 3pm demo, not just the labelled 30 in a batch.
- (constraint) Built with mlflow.genai.evaluate, not a hand-rolled scoring loop.
- (constraint) Read-only, unchanged: eval/labelled.csv, POLICY.md, BRIEF.md, seed/, and Epic 2's agent behavior -- this epic calls the existing agent as-is, never edits its decision logic, prompts, or policy handling.
- (constraint) CAP-5's judge always calls ChatGroq via JUDGE_MODEL/GROQ_API_KEY regardless of the agent's own PROVIDER setting, and never reads GEMINI_API_KEY -- so it never competes for the agent's Gemini quota.
- (constraint) No network calls beyond model APIs: decision_match, clause_match, reimbursable_total_match, and the flag-rate check all run locally against labels/seed data; only the agent's own model call and CAP-5's Groq call cross the network.
- (constraint) Unlike triage's Epic 3, no auto-approve-escalation handling is needed here: the expense agent (Epic 2 CAP-7) never pauses mid-run for a human, so the eval never blocks on that axis at all.
- (non-goal) Dashboards, CI, and hosting.
- (non-goal) Tuning the agent to raise its score.
- (assumption) Entrypoint assumed at cases/expense/eval/run_eval.py, report file at cases/expense/eval/latest_report.json -- mirrors triage's eval/run_eval.py and eval/latest_report.json pattern.
- (assumption) MLflow experiment reused as 'expense-agent' (same experiment Epic 2 assumed), not a separate eval-only experiment -- matches triage epic-3's pattern of logging into the agent's own experiment.
- (assumption) CAP-5's judge reports pass/fail per line item, averaged as a pass rate against the 0.75 target -- same treatment triage's rationale_judge used, since the PRD specifies the target at the WHAT level without prescribing a scale.
