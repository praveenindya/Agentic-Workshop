- (note) Input: PRD (Success Metrics SM-1..SM-C1), BRIEF.md 'How it's checked', cases/expense/eval/labelled.csv (line_id, claim_id, expected_decision, expected_clause -- no judge-notes column, no per-claim total column), spec-expense-epic-2/SPEC.md (adopted companion, the agent this evaluates), and triage's spec-epic-3 as a structural pattern reference only (not a source -- different case).
- (capability) CAP-1: a person can run uv run python cases/expense/eval/run_eval.py to evaluate the Epic 2 agent over every labelled line item in one pass, logging one MLflow run.
- (capability) CAP-2: decision_match scorer -- scores 1 when a line item's decision equals expected_decision, 0 otherwise, for every labelled row.
- (capability) CAP-3: clause_match scorer -- scores 1 when a line item's cited clause equals expected_clause, 0 otherwise.
- (capability) CAP-4: reimbursable_total_match scorer -- per labelled claim, scores 1 when the sum of that claim's expected-approve line items' amounts (from line_items.csv) equals the agent's own sum of its approved line items for that claim, 0 otherwise.
- (capability) CAP-5: an LLM judge scores explanation clarity and correct clause citation for each labelled line item's decision.
- (capability) CAP-6: after the run, a person sees and can reuse the eval's scores without opening the MLflow UI -- printed means for all scorers plus a held-for-approval count, and the same numbers written to a JSON report file.
- (constraint) Eval harness built with mlflow.genai.evaluate, not a hand-rolled scoring loop.
- (constraint) Read-only, unchanged: eval/labelled.csv, POLICY.md, and Epic 2's agent -- run_eval.py calls the existing agent as-is, never edits its decision logic or prompts.
- (constraint) The LLM judge always calls ChatGroq via JUDGE_MODEL/GROQ_API_KEY regardless of the agent's PROVIDER setting, mirroring triage's rationale_judge -- never competes for the agent's Gemini quota.
- (constraint) SM-C1 counter-metric: the eval must not reward defaulting ambiguous items to flag -- flagging everything trivially raises decision_match on some rows while producing an untrustworthy agent. No scorer or report treats flag as a safe default.
- (constraint) Only the first 30 claims (the labelled set) are scored by this epic; the last 10 (holdout) are scored live at the demo using this same harness, not a separate one.
- (constraint) The report JSON is the only new file this epic writes outside MLflow's own store, at cases/expense/eval/latest_report.json -- separate path from triage's eval/latest_report.json so the two cases' reports never collide.
- (non-goal) Dashboards, CI, and hosting.
- (non-goal) Tuning the agent to raise its score.
- (non-goal) Scoring the 10 holdout claims as part of this epic's own success signal -- that happens live at the demo, using the harness this epic builds.
- (assumption) SM-1 (decision_match) and SM-3 (clause_match) targets are 100% and reimbursable-total (SM-2) 100%, per the PRD -- treated as hard targets, not soft goals, since POLICY.md is a deterministic rule set with one correct answer per line item.
- (assumption) Judge target 0.75 of 1 (SM-3 in the PRD's numbering covers both clause-match and judge score under one label -- disambiguated here: clause_match is CAP-3's exact-match code scorer at 100%, and the LLM judge (CAP-5) targets 0.75 mean, treating pass as 1 and fail as 0 like triage's rationale_judge).
- (assumption) Held-for-approval count in the report (CAP-6) is computed the same way Epic 2 computes it -- decision==approve and amount>500 -- read from the run's outputs, not a new stored field.
- (event) Self-validate Pass 1 (Coherence): PASS -- 6 CAPs all have intent+success, intents are WHAT not HOW, 6 constraints each bend a real design choice, 3 non-goals present, success signal testable (exact numeric targets against labelled.csv), CAP IDs stable/unique, prose lean.
- (event) Self-validate Pass 2 (Preservation): PASS -- every load-bearing claim from PRD's Success Metrics (SM-1..SM-C1) and BRIEF.md's 'how it's checked' section landed in a CAP or Constraint. Wrapper-only drops: PRD's per-metric prose justification (e.g. why SM-2 follows from SM-1) -- rationale, not a testable claim itself.
- (event) SPEC.md derived and finalized for Epic 3.
- (direction) Story Breakdown: no checkpoints, same as Epics 1 and 2, for velocity.
- (decision) Story 1: Eval harness scaffold and code scorers -- implements CAP-1, CAP-2, CAP-3, CAP-4 together. All four are mlflow.genai.evaluate wiring plus straightforward code scorers with no LLM involved; splitting them further would just fragment one cohesive harness.
- (decision) Story 2: LLM judge -- implements CAP-5 alone, isolated because it is the only network-calling, non-deterministic scorer and needs its own test strategy (mocking the judge call).
- (decision) Story 3: Report output -- implements CAP-6 alone, testable directly against a fixed set of fake scores with no agent or judge run required.
- (event) Story Breakdown schema check: 3 entries, ids 1-3 unique and prefix-free, all quoted strings, no status field, required fields present on every entry -- PASS.
