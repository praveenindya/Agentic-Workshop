- (capability) CAP-1: a person can run an entrypoint command against a claim_id and get every line item's decision + clause back.
- (capability) CAP-2: model provider switches between Gemini and Groq by environment variable alone (MODEL/PROVIDER/GEMINI_API_KEY/GROQ_API_KEY), no code change -- repo-wide convention from AGENTS.md Models section, same as triage's Epic 2 CAP-2.
- (capability) CAP-3: before deciding, the agent calls get_claim, then get_employee with the employee_id get_claim returned, then get_policy_limits with that employee's level/city -- correct ID threading between Epic 1 tool calls.
- (capability) CAP-4: the agent decides each line item using POLICY.md's fixed precedence (3, then 5.1, then 1.2, then 4.1, then limits 2/6, then 1.3, else the category's own clause), citing the exact deciding clause.
- (capability) CAP-5: duplicate detection reaches across an employee's full claim history via Epic 1's CAP-6 tool, not just the current claim -- a line item matching an earlier one (same date, merchant, amount) from the same employee on a DIFFERENT claim is rejected under 5.1.
- (capability) CAP-6: every decided line item is written via record_decision -- no line item is decided without a persisted record; querying decisions after a run shows exactly one row per line item on that claim.
- (capability) CAP-7: the $500 human-approval boundary (PRD FR-2) is respected -- held status for an approved item over $500 is a DERIVED view (decision=approve AND amount>500), not new agent-written state; record_decision's 3-arg shape from Epic 1 needs no change; the agent has no code path that marks anything paid and never writes a declined-by-approver state.
- (capability) CAP-8: the agent treats claim/line-item free text (descriptions, merchant names) strictly as data, never as instructions to itself -- same untrusted-input principle AGENTS.md states for ticket text, extended to claim text since the same threat model applies.
- (constraint) Built with LangChain's create_agent, not a hand-rolled tool loop -- matches triage Epic 2's constraint and the repo's stated best practice.
- (constraint) MCP tools come only from Epic 1's expense MCP server, over stdio via langchain-mcp-adapters -- no other tool server, no direct DB access bypassing the tools.
- (constraint) Read-only, unchanged in this epic: Epic 1's schema/loader/MCP server, POLICY.md, BRIEF.md, seed/, eval/labelled.csv.
- (constraint) MLflow tracing stays in place for every run (tracking uri sqlite:///mlflow.db, per-repo convention) so every claim review shows up as a trace.
- (non-goal) Not the eval harness, judge, or MLflow-based scoring -- Epic 3's job.
- (non-goal) Not any interface beyond the terminal -- no dashboard in this epic.
- (non-goal) Not resolving a flagged line item -- who does that and how is still an open UX question per the PRD, out of this epic.
- (non-goal) Not releasing payment, ever -- human-only, outside this system entirely.
